Good question to ask mid-build. Let me walk through everything — what was built, why each decision was made, and how it works under the hood.

---

## 1. DESIGN SYSTEM — main.css + animations.css

**What changed:**
Two new CSS files replaced whatever styling existed before.

**Why:**
The old project had inconsistent styling because each page had its own CSS or inline styles. There was no single source of truth. Any change to a color or font required editing every file separately — which is exactly why the navbar looked different on every page.

**How it works:**
`main.css` defines CSS variables at the `:root` level:
```css
:root {
  --bg-primary: #0f1117;
  --accent: #22d3ee;
}
```
Every page reads from these variables. Change one variable, every page updates instantly. This is how theme switching works — `[data-theme="light"]` overrides the same variable names with light values. The browser applies whichever set is active on the `<html>` tag.

`animations.css` keeps all keyframes and hover transitions in one place so animations are consistent everywhere.

---

## 2. nav.js — Shared Navbar

**What changed:**
One JavaScript file that builds and injects the navbar HTML into any page that has `<div id="nav-root"></div>`.

**Why:**
Before, the navbar was copy-pasted into each HTML file separately. The moment you changed one thing — a link, the logo, button text — you had to update every single page manually. That's where the size and position inconsistency came from.

**How it works:**
Each page has an empty div:
```html
<div id="nav-root"></div>
```
When the page loads, `nav.js` runs and does:
```javascript
document.getElementById('nav-root').innerHTML = navHTML
```
Now there is exactly one navbar definition. Every page that loads `nav.js` gets the identical navbar automatically. Change it once, it changes everywhere.

The scroll behavior works by listening to `window.scroll` — after 50px it adds a `.scrolled` class which applies the frosted glass background via CSS.

---

## 3. theme.js — Dark/Light Toggle

**What changed:**
A dedicated JS file handles theme switching and persistence.

**Why:**
Without this, theme preference resets every time you navigate to a new page. Users would have to toggle every single page.

**How it works:**
On page load, `theme.js` reads `localStorage`:
```javascript
const saved = localStorage.getItem('neurachat-theme') || 'dark'
document.documentElement.setAttribute('data-theme', saved)
```
When toggled, it flips the `data-theme` attribute on `<html>` and saves the new value to `localStorage`. Since CSS variables are defined under `[data-theme="light"]`, the browser instantly re-renders every color on the page. The `transition` property on all elements makes this smooth instead of an instant flash.

---

## 4. cursor.js — Custom Cursor

**What changed:**
Two invisible div elements follow your mouse cursor — a small inner dot and a larger outer ring.

**Why:**
Adds a premium feel that signals the site was intentionally designed. Subtle enough to not distract, noticeable enough to feel different from a generic site.

**How it works:**
Two divs are positioned `fixed` with `pointer-events: none` so they don't interfere with clicks. JavaScript tracks `mousemove` events and updates their positions. The outer ring uses a lerp (linear interpolation) technique — it moves toward the cursor position slightly slower than the cursor itself, creating the lag/follow effect. On hover over buttons and links, the inner dot scales to zero and the outer ring expands — detected via `mouseenter` on all interactive elements. Disabled entirely on touch devices via `navigator.maxTouchPoints` check.

---

## 5. preloader.js — Page Preloader

**What changed:**
A full-screen overlay with the NeuraChat logo shows briefly on first visit, then fades out.

**Why:**
Two reasons — it masks the brief moment where fonts and assets are still loading (prevents layout flash), and it creates a polished first impression.

**How it works:**
On first load, a full-screen div covers the page. GSAP animates its opacity from 1 to 0 after 1.2 seconds, then sets `display: none`. A `sessionStorage` flag is set so it only shows once per browser tab session — not on every page navigation. Auth pages skip it entirely by setting the flag immediately in their HTML.

---

## 6. toast.js — Notification System

**What changed:**
A global notification system usable from any page with one line.

**Why:**
Before, error/success feedback was either missing or handled inconsistently — some pages used alerts, some had inline divs, some had nothing. Every interactive element needs feedback.

**How it works:**
`Toast.show('Message', 'success')` creates a div, appends it to the body bottom-right, animates it in via GSAP, waits 3 seconds, then animates it out and removes it from the DOM. Multiple toasts stack vertically. Four types — success (teal), error (red), info (blue), warning (amber) — each with their own color via CSS class.

---

## 7. animations.js — GSAP Animations + Particles

**What changed:**
All page animations centralized in one file using GSAP and ScrollTrigger.

**Why:**
CSS animations alone can't handle scroll-triggered sequencing or complex timelines cleanly. GSAP gives precise control over timing, easing, and sequencing.

**How it works:**

**Page load stagger:** Elements with class `.reveal` start invisible (`opacity: 0, y: 30`). GSAP animates them to `opacity: 1, y: 0` with 0.1s between each element. This is why the hero text, buttons, and mock chat appear sequentially instead of all at once.

**ScrollTrigger:** Watches the viewport. When a section enters 80% of the screen, it triggers that section's animation. This is why feature cards and pricing cards animate in as you scroll down index.html.

**Particles:** A `<canvas>` element sits behind everything with `z-index: 0`. JavaScript draws 60 small teal dots, moves them slowly every frame using `requestAnimationFrame`, and draws lines between any two dots within 120px of each other. When the browser tab is hidden (`visibilitychange` event), the animation pauses to save CPU.

---

## 8. protect.js — Auth Guard

**What changed:**
A small JS file that runs before anything else on protected pages.

**Why:**
Without this, anyone can type `/chat` or `/profile` directly in the browser and access the page even without being logged in. The backend might block the API calls but the page itself still loads.

**How it works:**
It calls `GET /api/auth/status` immediately. If the response is not authenticated, it redirects to `/login.html` before the rest of the page renders. Placed as the first script in `<body>` so it runs before any UI is painted.

---

## 9. index.html — Landing Page

**What changed:**
Complete rebuild of the marketing homepage.

**Why:**
The old index was either broken or not portfolio-ready. A proper landing page is the first thing a recruiter or visitor sees.

**How it works:**
Ten sections each with their own semantic purpose — hero converts visitors, features explains the product, pricing sets expectations, testimonials build trust, FAQ reduces friction, CTA drives signups. Each section is a self-contained `<section>` tag with anchor IDs so the navbar links scroll directly to them.

## 10. chat.html + chat.js + chat.css

**What changed:**
Complete rebuild of the chat application interface.

**Why:**
The old chat had broken history, no empty state, inconsistent styling, and broken membership enforcement.

**How it works:**

**Sidebar:** Fetches `GET /api/chats` on load and groups results by date. Each item is clickable — calls `GET /api/chats/<id>/messages` and renders that conversation. New chat calls `POST /api/chats/new`, gets back a `chat_id`, sets it as `state.currentChatId`.

**State management:** A `state` object holds `currentChatId`, `isLoading`, and `limitReached`. All functions read from and write to this object so the UI stays in sync.

**Sending messages:** Input value is read, appended to the UI immediately (user bubble), then sent to `POST /api/chat` with `chat_id`. While waiting, a typing indicator shows. When response arrives, it's rendered through `marked.parse()` wrapped in `DOMPurify.sanitize()` — this converts markdown to HTML safely without XSS risk.

**Membership:** On load, fetches profile to get `message_count` and `message_limit`. Renders a progress bar. At 5 remaining shows warning. At limit, hides the composer entirely and shows the upgrade block. Pro plan hides the entire membership UI.

---

## 11. login.html + register.html + auth.js

**What changed:**
Complete rebuild of auth pages with proper validation, error handling, and backend wiring.

**Why:**
Old login had hardcoded `localhost` URLs which broke on deployment. No client-side validation meant bad requests were hitting the backend unnecessarily.

**How it works:**

**Validation:** `auth.js` validates email format with regex and password length before any fetch call. If invalid, shakes the card (GSAP `x` oscillation) and shows inline error messages. No network request is made for obviously wrong input.

**Fetch:** Uses `credentials: 'same-origin'` — critical for Flask sessions. Without this, the browser doesn't send the session cookie with the request, so Flask can't identify the user even after login.

**Error mapping:** API error codes are mapped to human-readable messages:
- `USER_NOT_FOUND` → "No account found with this email"
- `WRONG_PASSWORD` → "Incorrect password"

**Password strength:** Four levels calculated by checking length, uppercase, numbers, and special characters. Updates a colored bar in real time on `input` event.

**Remember me:** Stores email in `localStorage` on successful login if checked. On page load, pre-fills the email field if a stored value exists.

---

## 12. Bug Fix — Chat Engine

**What changed:**
Three bugs fixed in `engine.py` and `agent.py`.

**Why they existed:**
The agentic engine was built for V2 which had a different architecture. When V3 added conversation history, the function signatures weren't updated to match.

**Bug 1 — Missing message parameter:**
`ask_agent()` wasn't accepting the current user message as a parameter. It only received memory fields and history. The actual question was never sent to Gemini.

**Bug 2 — System prompt in wrong position:**
The system prompt was appended as a `user` role message at the end of `contents`. Gemini read this as the user's latest question and responded to the instruction instead of the actual question. Moving it to `system_instruction` in the config tells Gemini it's a background instruction, not a conversational turn.

**Bug 3 — Typo:**
`uesr_question` instead of `user_question`. Python is case and spelling sensitive — one wrong character and the variable doesn't exist.
